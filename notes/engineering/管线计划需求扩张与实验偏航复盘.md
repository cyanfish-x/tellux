> 2026-09-12。用户要求重新评估计划、总结错误并防止复发；本记录与[纠偏计划](../decisions/统一场景渲染与大气透明合成架构.md)共同维护。事实来源为原始对话、已提交方案、当前源码及历史实验报告。本轮未重新运行 GPU 或浏览器实验。

## 结论

这次主要失误是**把方案完整性当作用户目标，把实验参考变成实施主线**。问题起点是高斯在地平线被天空覆盖，以及类似问题反复出现；用户希望有遮挡正确、性能良好的成熟管线。我将“成熟”自行展开为更全面的物理合成能力，又让这些扩展反过来约束主线。

具体后果包括：新增折射研究、完整联合积分和区间重建被放进统一前置门槛；高成本实验继续派生采样微优化，正式编排仍未落地。原始实验有数值和工程价值，但这些价值不证明其属于用户目标的最短实施路径。

## 2. 因果判断与证据边界

以下是根据上述行为作出的流程判断，不声称能从日志证明不可观察的心理动机。

### 2.1 缺少需求来源，兼容检查升级成新增能力

“分阶段后不要破坏原生玻璃”与“实现云内真实折射”分别是兼容约束和新功能。旧计划把二者写在同一张能力表里，没有来源和范围标签，后续审查自然把新功能当作已有承诺。

**对应纠正**：当前计划第 1 节以用户已确认意图为唯一范围入口；保留既有材质回归，A2 退出本次主线。

### 2.2 技术审查没有检查必要性

指出“视线区间不能覆盖折射路径”在技术上有意义，但首先应该审查新增折射是否需要。把建议写入计划，再以计划为依据产生更严的审查项，形成了文档互相背书。

**对应纠正**：每条新门槛先回答“需求来自哪里、阻止什么实际失败”；不能只引用 Agent 编写的另一份方案。

### 2.3 从信息缺口直接跳到了更大的算法路线

最终云颜色／代表深度不足以表达任意穿插，是接口信息不足的证据；它不证明必须重写云步进，也不证明当前目标必须达到任意层数的精确积分。

**对应纠正**：先验证可复用的编排和深度接缝；穿云缺口以最小真实用例取证。必要扩展优先保留原天气、密度、照明、步进与低分辨率流程，新增输出的历史单独验收。

### 2.4 参考、候选和生产成本的沟通不清

历史 A1 记录的 13.76 ms GPU p50 是额外参考积分 draw，尚不包括原流程；之后约 2 ms 的整帧数据对应在原云流程上修改的快速候选。二者不能当成同一实现的优化前后。

报告自身已有这些限制，问题是推进决策和状态摘要没有充分围绕“这些测量到底决定什么”组织。修复参考条带、检查采样收敛有价值，但不能据此持续追加不服务当前遮挡缺口的优化。

**对应纠正**：参考只为一个可判断的问题服务；原方案、独立修复、生产候选分别计量。结论足以否定或支持路线后停止研究扩展。

### 2.5 用“成熟引擎”作笼统背书

“实时渲染会近似”无法回答选择了什么算法、解决什么场景。UE 的体积雾、体积云、空气透视有不同资源与能力，Unity 的 URP 图管理也不能证明 HDRP 云的遮挡。

**对应纠正**：计划列出官方来源、版本／路径、可借鉴部分及不可外推的部分；成熟引擎采用是选型证据，Tellux 接入仍需实测。

## 3. 防复发规则：触发时做什么

本次用户已确认“落实防复发规则”。以下在项目计划和实验工作中执行，通过根 AGENTS.md 与 notes 入口接入；不依赖自动后台监控。

| 触发点 | 必须产生的最小结果 | 如何阻止同类错误 |
| --- | --- | --- |
| 新增一个目标或“必须通过”项 | 标明用户需求／既有兼容／实现建议，附来源和具体失败用例 | 新玻璃能力不能冒充原生材质兼容要求 |
| 准备绕过上游流程或重写核心算法 | 写出已复用什么、具体缺口、更小方案失败的证据、预计新增 draw／资源和维护边界 | 从“接口不足”到“整体重写”之间增加必要性检查 |
| 启动边界实验 | 一段实验约定：要判断的问题、原基线、唯一主要变化、预期观测、停止条件、下一步选择 | 先知道何时足够，而不是实验越完整越好 |
| 正确性实验开始派生性能微优化 | 检查该候选是否已证明解决目标；分别标明参考与生产路线 | 避免花时间优化一个不能解决遮挡问题的表示 |
| 范围／性能／上游改动超出原约定 | 停止依赖该变化的扩展，输出可审查差异与替代方案；继续不依赖它的常规工作 | 不静默扩大能力或放宽质量，不把所有工作无谓停住 |
| 自审、评审或任务交接 | 先审目标必要性，再审算法正确性，最后审性能与维护成本 | 评审不再只是把自己的方案补得更大 |
| 汇报完成度 | 分开说明实现存在、实验执行、行为验收、性能结论及未完成项 | 不用“测试通过”替代实际效果，也不把旧报告用于更新后的代码 |

“写清楚”应在已有计划、实验记录或任务说明中完成，不强制每次新建文档。正常实现、调试和验证无需再次审批；新增能力、更换核心算法或改变已确认质量目标则需基于具体差异重新审查。

### 后续方案的简短自检

1. 每项工作能否追溯到用户目标或实际兼容失败，而不是“成熟引擎应该都有”？
2. 上游的原流程是否真正复用，还是只复制函数后重新实现了调度和积分？
3. 若某实验失败，究竟阻塞哪一步？是否错误地阻塞了无关基础编排？
4. 是否在用更大步数、更多附件或更强物理模型补救一个尚未证明必要的设计？
5. 当前证据能否回答目标问题？若能，为什么还需要继续扩展实验？
6. 所谓“最佳实践”是否有具体来源、模式和限制？是否误把雾／普通网格的结论用于云／高斯？
