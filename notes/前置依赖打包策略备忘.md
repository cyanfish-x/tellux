# 前置依赖打包策略备忘

本文记录 tellux 对前置依赖（three、3d-tiles-renderer、takram 系列等）打包策略的评审结论，用于回看与决策对齐。

## 结论

前置依赖**不应参与打包**。维持当前 `external` + `peerDependencies` 设计，由消费者自行提供这些依赖。

适用场景：

- 评审或调整 `vite.config.ts` 的 `external` 列表。
- 变更 `package.json` 的 `dependencies` / `peerDependencies` / `devDependencies` 分类。
- 评估是否把某个第三方依赖打进 lib 产物。
- 处理 three 单例、双实例运行时报错或第三方类型不兼容问题。

## 当前打包策略现状

`vite.config.ts` 已明确把所有核心前置依赖声明为 `external`（产物里只保留 `import` 引用，不内联实现）：

```ts
// vite.config.ts 第 29–40 行
const external = [
  '3d-tiles-renderer',
  '3d-tiles-renderer/plugins',
  '@takram/three-atmosphere',
  '@takram/three-clouds',
  '@takram/three-geospatial',
  '@takram/three-geospatial-effects',
  'postprocessing',
  'three',
  'three/webgpu',
  /^three\/addons\//
]
```

产物形态（`vite.config.ts` 第 48–56 行）：

- 纯 ESM：`formats: ['es']`，无 CJS / UMD。
- 多入口：`index` + `assets`，输出到 `dist/`。
- `src/index.ts`、`src/assets.ts` 之外的代码（`actions/` 部署脚本）不进入 lib 产物。

依赖分类与 `package.json` 一致：

- 7 个核心前置依赖全部声明为 `peerDependencies`，且被 `external` 覆盖。
- `@mapbox/vector-tile` / `pbf` 标记为 `peerDependenciesMeta.optional`，且不在 `external` 中，因此会内联进产物（体积小，可接受）。

## 为什么不能打进包

### 1. three.js 是全局单例型依赖，双实例会直接崩溃

- `three` 在 `src/` 下被约 48 个文件引用，并大量使用 `three/addons/*`（GLTFLoader、DRACOLoader、Line2 系列、RoomEnvironment、BufferGeometryUtils）和 `three/webgpu`。
- three 的 `Object3D` / `Material` / `Renderer` 内部事件系统、对象比较、`instanceof` 判定都依赖**全模块唯一实例**。一旦嵌套进任何一份 three 副本，就会出现"用户 three 创建的对象传给 tellux 的 three 时类型不兼容、材质/几何失效"的双实例问题。
- 这是 Three.js 生态铁律：所有 three 插件库都把它放 `peerDependencies`。

### 2. 公开 API 直接 re-export 了第三方类型，强制它们必须是 peer

`src/index.ts` → `src/Viewer.ts` 的公开类型表面包含：

- 来自 three / three/webgpu：`TelluxRenderer` / `TelluxWebGLRenderer` / `TelluxWebGPURenderer`（底层是 three renderer），`FlyToTargetTarget` 里的 `THREE.Object3D`。
- 来自 3d-tiles-renderer：`TilesRenderer`（出现在 `TilesetLayer.tileset`、拾取结果类型）、`GlobeControls`。

用户写 TypeScript 时会 `import type` 这些类型，**类型实例必须与用户自己装的版本对齐**。打进包会导致类型"重复声明 / 不兼容"。

### 3. takram 全家桶 / postprocessing / 3d-tiles-renderer 自身 `peerDependencies.three`

- `3d-tiles-renderer`（约 18 文件）、`postprocessing`（2 文件）、4 个 `@takram/*`（5 文件）自身内部都直接 `import 'three'`，运行时必须拿到宿主的**同一个** three 实例。
- 把其中任何一个打进 tellux 产物，都会牵出"我有一份 three，宿主又有一份"的冲突。

### 4. takram 非纯 JS，GLSL 内联，打入只增体积

- takram 包的 GLSL 被**内联打包**进它自己的 `shared*.js` / `webgpu.js`（如 `@takram/three-atmosphere` 的 `shared.js` ≈ 156KB，含大量 shader）。
- 依赖链互锁：`three-clouds` → `three-atmosphere` + `three-geospatial`；`three-atmosphere` → `three-geospatial` + `astronomy-engine`。
- 即便 takram 声明 `sideEffects: false`，因 GLSL 内联 + 互锁依赖 + 共享 three 实例，tree-shake 收益极低。打进包内**只增体积、不解决问题**。

## 依赖分类对照表

| 依赖 | 当前归属 | 是否应打包 | 理由 |
|---|---|---|---|
| `three` (+ `/webgpu`, `/addons/*`) | peer + external | ❌ | 全局单例；公开 API re-export 类型；下游库均 peer 依赖它 |
| `3d-tiles-renderer` (+ `/plugins`) | peer + external | ❌ | 全局单例；公开 API re-export `TilesRenderer`/`GlobeControls` |
| `@takram/*`（atmosphere / clouds / geospatial / geospatial-effects） | peer + external | ❌ | 内部直接 `import 'three'`；GLSL 大体积；依赖链互锁 |
| `postprocessing` | peer + external | ❌ | three 的 postprocessing 库，绑定宿主 renderer |
| `@mapbox/vector-tile` / `pbf` | optional peer，已内联 | ✅ 可接受 | 体积小；`src/` 不直接 import，由 3d-tiles-renderer 消费 |
| `dotenv` / `tencentcloud-sdk-nodejs-cdn` | `dependencies`（误置） | — | 仅 `actions/` 部署脚本用，不进 lib 入口 |

## 已知的小瑕疵（不影响打包方向）

`dotenv`、`tencentcloud-sdk-nodejs-cdn` 仅用于 `actions/` 部署脚本，不进入 `src/index.ts` / `src/assets.ts` 入口，但当前留在 `dependencies`：

- 后果：消费者 `npm install tellux` 时会无谓拉取这两个 Node 侧工具。
- 建议方向（可选后续动作）：移到 `devDependencies`。
- 本次评审**不执行**该调整，仅记录。
