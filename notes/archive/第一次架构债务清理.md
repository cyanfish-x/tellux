# 第一次架构债务清理：保留的理由

> 历史评审摘要。2026-09-06 删除重复的类职责罗列、旧行数和已过时的实施清单；本文件不维护当前债务优先级。原文可由本地 Git 基线恢复，见 [重建记录](2026-09-06-知识重建记录.md)。

## 为什么做第一次拆分

- Viewer 同时做装配、DOM 事件、尺寸、模型、widgets 和采样调度，变更半径过大。拆分的目的在于让资源和副作用有明确所有者，不是机械减少一个文件的行数。
- TilesetManager 混合表面、地形、影像、场景瓦片和采样池。工厂与 adapter 的边界能隔离上游变化；当时建议继续拆 registry / scheduler，不等于现在仍需按相同类名拆分。
- 相机通过 camera.userData 反查 tileset，是未声明且可能与应用冲突的依赖。当前已使用显式 ellipsoid provider，不能恢复旧隐式协议。
- Scene 与大气/云底层控制混杂用户态和底层态。当前快照应用边界见 [状态所有权](../engineering/Scene与AtmosphereManager双状态坑点.md)，其中允许派生态缓存。
- 源码层类型检查不能覆盖 URL、状态失效、采样 readiness、资源释放与 shader 文本协议。这解释了补充测试的价值，不再保留“尚无测试脚手架”的旧结论。

## 仍需按实际变更判断的风险

- 上游 readiness / raycast 字段不是公共稳定协议；TilesetSamplingAdapter 收敛读取点并不消除升级风险。
- 构造和销毁仍需要组合根编排；拆 manager 不自动证明失败回滚和异步取消完整。
- widgets 静态依赖与公开 barrel 中转会影响包边界。但拆独立入口或重排 exports 会改变消费者契约，不能只因旧债务清单建议就执行。
- shader 字符串替换依赖上游 hook；当前已有 AtmosphereShaderPatches 和 PositionPipeline，不能继续把“拆出 helper”当作未完成事实。升级仍应查具体匹配和失败行为。

上述风险是评审理由与复核触发条件，不是本次重新确认的缺陷。完整后续缺陷、修复提交和当时验收见 [2026-07-30 引擎健康诊断](引擎健康诊断-2026-07-30.md)；当前职责见 [项目架构](../architecture/项目架构.md)，公开面边界见 [API 决策](../decisions/API稳定版设计决策.md)。
