1. 当前基础盘是否足够稳定；
2. 哪些问题已经构成真实缺陷或高风险边界；
3. 在继续增加大型功能前，最值得先偿还哪些债务；
4. 每项整改如何验证完成，而不是只靠代码看起来合理。

## 1. 结论摘要

Tellux 当前基础盘总体健康：

- TypeScript 严格类型检查通过；
- 32 个测试文件、104 项测试全部通过；
- 库构建、声明生成、文档与示例生产构建均可完成；
- 生产依赖审计未发现已知漏洞；
- `Viewer` 已形成明确的组合根，主要子系统拥有独立 manager / controller / factory；
- `destroy()` 覆盖了主要资源、监听器和渲染对象，整体资源释放意识良好。

但当前还不是适合继续无保护堆叠大型能力的状态。审计确认的 5 项 P1 风险 EH-001 至 EH-005 均已完成修复：

1. 已删除的影像图层句柄可以重新创建“幽灵 overlay”；
2. 实体颜色补偿使用模块级全局状态，多个 Viewer 会相互污染；
3. `pickAll` 的实际行为不符合“全部命中”的公开契约；
4. 详细高度采样无法完整取消，直接地形请求和缓存生命周期失控；
5. HISM 拾取会永久覆盖宿主应用的 `THREE.Mesh.prototype.raycast`。

此外，关键异步生命周期、规模化拾取路径以及公开 API 与实现的一致性仍需继续收口。

**原审计建议：先完成一轮 P1 稳定性整改，再扩展大型能力。** 后续整改已记录在各 EH 条目与退出标准中；本次整理没有重跑这些验证，不据此重新判定当前可发布性。

## 2. 优先级和判定口径

### 2.1 优先级

- **P1**：已确认的行为缺陷，或可能破坏 Viewer 隔离、资源生命周期、宿主应用稳定性的高风险问题。应在新增大型能力前处理。

- **P3**：公开 API、文档和内部规范上的债务。当前有降级或说明，但继续扩散后修改成本会显著上升。

## 3. 健康基础

### 3.1 组合根和职责拆分方向正确

`Viewer` 仍然较大，但当前主要承担公开门面和组合编排职责。以下能力已经有明确所有者：

- 渲染器适配：`RendererAdapter`
- 帧循环：`ViewerRenderLoop`
- viewport 生命周期：`ViewportResizeManager`
- DOM 交互：`ViewerInteractionManager`
- 模型生命周期：`ModelManager`
- 目标飞行：`TargetFlightController`
- tileset / terrain / imagery：`TilesetManager` 及其 factory
- 高度采样：`HeightSampler`
- 大气和后处理：对应 rendering manager

这说明项目已经从“所有逻辑堆在 Viewer”转向可演进的领域模块，不需要为了本次审计进行大规模重写。

### 3.2 销毁路径覆盖较完整

[src/Viewer.ts](../../src/Viewer.ts) 的 `destroy()`（约 1038 行）具备幂等保护，并依次释放：

- 飞行、render loop、viewport 和交互监听；
- 模型、HISM、高亮、实体、贴地和 widget；
- 高度采样、目标飞行、后处理和大气；
- tileset、controls、DRACO loader 和 renderer；
- Viewer 创建的 canvas DOM。

事件型子系统也普遍拥有对称的 `dispose()`，这是当前架构的重要正向基础。

### 3.3 现有测试已有实际价值

测试已经覆盖以下高价值区域：

- Entity / Object / Scene Picker；
- HISM 聚类、LOD、RTC、BVH 缓存、拾取和运行统计；
- 高亮、Symbol、SDF 和遮挡 pass；
- imagery / terrain overlay；
- WebGPU renderer adapter、大气和 controls；
- 天地图瓦片和高度图转换。

问题不在于“没有测试”，而在于测试范围尚未覆盖本轮发现的状态失效、异步取消和真实浏览器集成边界。

## 4. P1 诊断

### EH-001：删除后的影像图层句柄可复活 overlay

**分类：已确认缺陷**

**处理状态：已完成**

**修复提交：`ce1981a`（`fix: 防止已移除影像图层句柄复活`；2026-09-06 在 HEAD 祖先日志中核对）**

#### 证据链

1. [src/LayerManager.ts](../../src/LayerManager.ts) 的 `remove()`（约 147 行）只把图层从 `layers` 数组移除；
2. 返回给用户的 `ImageryLayer` 句柄仍持有 owner；
3. 该句柄之后执行 `setVisible()` 或 `setStyle()`，仍会调用 owner 的 `update()`；
4. [src/Viewer.ts](../../src/Viewer.ts)（约 546 行）收到 visibility / style 变化后，直接调用 `tilesets.syncImageryLayer(change.layer)`；
5. [src/tiles/TilesetManager.ts](../../src/tiles/TilesetManager.ts)（约 478 行）发现 overlay 不存在且图层可见时，会重新创建 overlay；
6. `getLayerOrder()` 对已不在权威列表中的图层返回列表尾部位置。

因此，下面的调用序列可以产生一个不在 `viewer.layers.getAll()` 中、但仍参与渲染的 overlay：

```ts
const layer = viewer.layers.add(options)
layer.remove()
layer.setStyle({ opacity: 0.5 })
```

`removeAll()` 后保留的旧句柄具有相同风险。如果之后添加了相同 id 的新图层，旧句柄还可以通过 `moveTo()` 或 `remove()` 误操作替代图层。

#### 影响

- 图层列表状态与真实渲染状态分裂；
- 业务侧无法通过 `getAll()`、排序或批量移除管理该 overlay；
- 后续 terrain / surface 重建时，幽灵 overlay 的行为可能再次变化；
- 形成难以从 UI 状态解释的“图层已删除但画面仍出现”问题。

#### 推荐整改

- `ImageryLayer` 增加显式 active / disposed 状态；
- `remove()` 和 `removeAll()` 必须让对应句柄失效；
- owner 在处理 update / move 前再次验证句柄仍属于权威集合；
- 明确失效句柄的 API 语义：统一 no-op 或统一抛出可识别错误，不要部分生效；
- `TilesetManager` 不应仅凭一个外部句柄决定创建 overlay，应以当前权威图层集合为准。

#### 验收标准

- 覆盖 `remove()`、`removeAll()` 后调用 show / style / move 的回归测试；
- 被删除句柄不能重新创建 overlay；
- `LayerManager` 权威集合和所有 tileset overlay 集合保持一致；
- terrain / surface 切换后不会恢复已删除图层。

#### 处理结果

- 句柄与 owner 的连接改由模块内 WeakMap 管理；
- `remove()` / `removeAll()` 在发出结构变化前断开旧句柄；
- 失效句柄保留移除时的只读快照，后续 name / visibility / style / order 写操作均为 no-op；
- 失效句柄重复 `remove()` 返回 `false`；
- owner 回调增加对象身份校验，旧句柄不能影响同 id 替代图层；
- 新增 [src/test/layerManager.test.ts](../../src/test/layerManager.test.ts)，覆盖句柄移除、manager 移除、`removeAll()` 和同 id 替代图层；
- 修复后 `pnpm type-check` 通过，33 个测试文件、107 项测试全部通过。

### EH-002：色调映射补偿使用模块级全局状态

**分类：已确认缺陷**

**处理状态：已完成**

**修复提交：`e15e722`（`fix: 隔离 Viewer 色调映射颜色状态`；2026-09-06 在 HEAD 祖先日志中核对）**

#### 证据链

[src/entities/invertToneMapping.ts](../../src/entities/invertToneMapping.ts)（约 158 行）维护：

```ts
let activeToneMapping
let activeToneMappingExposure
```

`Viewer` 构造和 `toneMappingExposure` setter 都通过 `setToneMappingState()` 修改这份模块级状态。所有使用 `resolveColor()` 的实体和高亮对象共享它。

这会产生两个独立问题：

1. **多 Viewer 污染**：最后创建或修改曝光的 Viewer 决定所有 Viewer 后续颜色解析结果；
2. **单 Viewer 状态漂移**：修改曝光只更新 renderer 和全局解析参数，已有材质中按旧曝光计算的预补偿颜色不会自动刷新。

#### 影响

- 多 Viewer 页面无法保证彼此隔离；
- 同一个 Viewer 中，曝光修改前后创建或改色的实体可能表现不一致；
- 用户态颜色和 renderer 实际状态不再同构；
- 高亮、点、线、面等多个模块被同一全局状态耦合。

#### 推荐整改

优先建立 Viewer 级 `ColorResolver` / `DisplayColorTransform`：

- 每个 Viewer 拥有独立的 tone mapping 与 exposure 状态；
- Entity、Highlight 等系统通过显式依赖获得颜色解析能力；
- 图形对象保留用户传入的语义颜色，而不是只保存补偿后的材质颜色；
- exposure 改变时，由 Viewer 统一刷新受影响的 graphic；
- 长期可评估把补偿移到 shader uniform，减少 CPU 重算。

不建议通过“创建实体前再次写全局变量”规避，这仍然无法解决并发 Viewer 和已有材质刷新问题。

#### 验收标准

- 删除 `invertToneMapping.ts` 中可变的 Viewer 运行时全局状态；
- 两个不同 exposure 的 Viewer 同时存在时颜色互不影响；
- 修改 exposure 后已有实体和高亮仍保持目标显示色；
- WebGL / WebGPU 或不同 tone mapping 路径拥有明确降级语义；
- 增加多 Viewer 和运行时 exposure 变更测试。

#### 处理结果

- 删除模块级 `activeToneMapping` / `activeToneMappingExposure` 和 `setToneMappingState()`；
- 新增 Viewer-owned `ToneMappingColorResolver`，Entity 与 Highlight 通过显式 `ResolveColor` 依赖使用当前 Viewer 状态；
- 点、普通/贴地折线、普通/贴地多边形保留语义颜色，并由 `EntityManager.refreshColors()` 统一重算；
- `toneMappingExposure` setter 更新当前 Viewer 的 resolver 后，刷新已有实体和高亮；
- 默认解析器保持 AgX / exposure 1 的兼容降级，直接构造 `Entity`、`EntityManager` 或 `HighlightManager` 不会新增必填参数；
- 新增 [src/test/toneMappingColorResolver.test.ts](../../src/test/toneMappingColorResolver.test.ts)，覆盖双 resolver 隔离、普通与贴地图形刷新、高亮隔离和 Viewer setter 刷新。
- 修复后 `pnpm type-check` 通过，34 个测试文件、112 项测试全部通过；仍有的 3 条 `CesiumIonAuthPlugin` 弃用警告归 EH-006 处理。

### EH-003：`pickAll` 未返回全部命中

**分类：已确认缺陷**

**处理状态：已完成**

**修复提交：`4d596df`（`fix: 补全 pickAll 全量拾取语义`；2026-09-06 在 HEAD 祖先日志中核对）**

#### 公开契约

- [src/Viewer.ts](../../src/Viewer.ts)（约 834 行）：`Picks all selectable objects`
- [docs/guide/interaction.md](../../docs/guide/interaction.md)（约 89 行）：合并各层全部命中，由近到远
- [docs/api/viewer.md](../../docs/api/viewer.md)（约 167 行）：返回由近到远的全部命中
- click 事件的 `picks` 也被描述为完整 `pickAll`

#### 实际行为

[src/sampling/ScenePicker.ts](../../src/sampling/ScenePicker.ts)（约 104 行）中：

- Entity 使用 `pickEntities()`，返回多个命中；
- Object 使用 `pickObjects()`，返回多个命中；
- HISM 使用单数 `hismManager.pick()`，只返回全局最近实例；
- 3D Tiles 使用单数 `tilesetFeaturePicker.pick()`，只返回全局最近 feature。

现有 `scenePicker.test.ts` 只为 HISM / feature 各提供一个结果，因此没有覆盖该契约缺口。

#### 影响

- 叠层查询、点击穿透、候选列表和业务 drill picking 获得不完整结果；
- 相同 API 对不同 domain 使用不同的“all”语义；
- 文档建议用户在 mousemove 中显式调用 `pickAll` 获取完整列表，但实际仍不完整。

#### 推荐整改

先明确一个不可含糊的 API 决策：

##### 方案 A：保留真正的 `pickAll`

- 为 HISM 和 3D Tiles 增加 all-hit 实现；
- 按距离做全局排序；
- 提供 `limit`、layer 过滤和必要的性能保护；
- nearest-only 路径继续由 `pick()` 使用。

##### 方案 B：承认当前是“每域最近”

- 修改方法名、类型和全部文档，避免继续叫 `pickAll`；
- 另行提供真正的 drill API。

当前已有用户文档明确承诺“全部命中”，优先推荐方案 A。

#### 验收标准

- 测试同一屏幕位置命中多个 HISM 实例、多个 tileset feature；
- 返回结果跨 domain 严格按距离排序；
- `event.picks` 与直接调用 `viewer.pickAll()` 语义一致；
- 文档、JSDoc、类型注释和运行时行为一致；
- 大规模场景下有明确的 limit 或性能边界。

#### 处理结果

- HISM 增加 all-hit 路径，每个 RTC instance 保留最近交点，并按图层、簇、原型和实例身份去重；
- 3D Tiles 增加 all-hit 路径，按 Object3D 与 feature id 组合去重；
- Object 层按 Object3D 去重，避免同一 mesh 的多个三角面交点重复暴露；
- `ScenePicker.pickAll()` 汇总全部 domain 后执行全局距离排序，nearest-only 的 `pick()` 路径保持独立；
- `ViewerPickOptions` 增加 `limit`，只在全局排序后截断返回值，并在文档中明确它不会减少各层内部遍历；
- 新增 HISM 多实例/多 part、Tiles 多对象、Object 去重、跨 domain 排序和 limit 回归测试。
- 修复后 `pnpm type-check` 通过，35 个测试文件、118 项测试全部通过；仍有的 3 条 `CesiumIonAuthPlugin` 弃用警告归 EH-006 处理。

### EH-004：详细高度采样取消与缓存生命周期不完整

**分类：高风险设计**

**处理状态：已完成**

**修复提交：`2d74b84`（`fix: 收口详细高度采样生命周期`；2026-09-06 在 HEAD 祖先日志中核对）**

#### 证据链

[src/sampling/HeightSampler.ts](../../src/sampling/HeightSampler.ts) 中：

- `cancelMostDetailedSampling()` 只清理 `heightSamplingJobs`；
- direct terrain 路径直接等待 `QuantizedMeshTerrainSampler.sampleMostDetailed()`；
- hybrid 路径会并行启动 terrain Promise 和 tileset job；
- `waitForBrowserPaint()` 的 rAF / timeout 没有 disposed 或 generation 检查。

[src/sampling/QuantizedMeshTerrainSampler.ts](../../src/sampling/QuantizedMeshTerrainSampler.ts) 中：

- fetch 没有接收 `AbortSignal`；
- `layerCache` 和 `tileCache` 是无容量上限的 Map；
- decoded terrain tile 会一直保留到 `dispose().clear()`；
- `setTerrain()` 只取消 Viewer 的队列任务，不会清理 direct sampler 缓存。

#### 影响

- 切换 terrain 后，旧 terrain 请求仍可能完成并返回结果；
- hybrid 采样可能合并已过期 terrain 数据和已取消的 tileset 部分结果；
- Viewer 销毁后网络和解析任务仍继续占用资源；
- 长时间跨区域采样会持续保留 decoded quantized-mesh 数据；
- 多次切换 terrain 会保留旧数据源的缓存。

#### 推荐整改

引入统一的 `HeightSamplingSession` 或 generation token：

- 每次采样绑定 session ID 和 `AbortController`；
- terrain 切换、图层结构变化、Viewer destroy 时使 session 失效并 abort；
- 每个 await 边界后检查 session 是否仍有效；
- 明确取消语义：推荐 reject `AbortError`，或者定义显式 cancelled result，避免把部分结果伪装成正常完成；
- cache 按 terrain resource 分区；
- tile cache 使用 LRU / 容量预算，并在 terrain 切换时清理不再可达的数据源；
- 失败 Promise 不应永久留在 cache 中。

#### 验收标准

- terrain 切换和 Viewer destroy 能中止尚未完成的 fetch；
- 旧 session 不能在新 terrain 上提交结果；
- hybrid 路径取消时不会继续等待旧 terrain Promise；
- cache 有可测试的容量上限和淘汰策略；
- 覆盖取消、切换、失败重试、并发去重和缓存淘汰测试。

相关实现背景参见 [sampleHeightMostDetailed 实现链路](../architecture/sampleHeightMostDetailed实现链路.md)。

#### 处理结果

- 每次 most-detailed 调用由独立 `HeightSamplingSession` 贯穿等待 paint、terrain 直采、tileset job 与 hybrid 合并；
- terrain / 采样图层切换和 Viewer 销毁统一使 session 失效，取消以 `AbortError` 拒绝，不再 resolve 部分结果；
- 等待 paint 的 rAF / timeout、terrain endpoint、`layer.json` 和 `.terrain` fetch 均进入可取消链路；

- direct sampler 两级缓存改为可中止异步 LRU，默认上限为 2 个 layer resource 和 64 个 decoded tile；
- 缓存保留同 key 并发去重，失败 / 取消项立即淘汰，terrain 切换清空旧 resource；
- Viewer 在新增、移除或切换 3D Tiles 可见性时同步取消依赖旧图层集合的采样；
- 新增等待 paint、Viewer dispose、terrain 切换、队列取消、hybrid 取消、并发去重、失败重试及两级 LRU 淘汰测试。

### EH-008：异步初始化失败缺少统一收口

**处理状态：已完成**

**修复提交：`cdecefd`（`fix: 收口 Viewer 与模型异步失败生命周期`；2026-09-06 在 HEAD 祖先日志中核对）**

#### Viewer

[src/Viewer.ts](../../src/Viewer.ts) 的 `Viewer.create()`：

```ts
const viewer = new Viewer(container, options)
await viewer.ready
return viewer
```

如果 WebGPU `renderer.init()` 拒绝，factory 会直接抛错，但不会调用 `viewer.destroy()`。此时 canvas、监听器以及构造阶段已创建的 manager 可能继续留存。

构造函数本身也在 append canvas 后继续装配大量子系统，没有统一的异常回滚栈。

#### Model

[src/models/ModelManager.ts](../../src/models/ModelManager.ts) 使用 `void model.load()` 启动加载；[src/models/GltfModelLayer.ts](../../src/models/GltfModelLayer.ts) 在失败或“加载完成前已删除”时 reject 独立的 `ready` Promise。若调用方从不观察 `model.ready`，可能产生 unhandled rejection。

#### 推荐整改

- `Viewer.create()` 在 `ready` 失败时保证调用 `destroy()`；
- 中期引入构造期 `ResourceScope` / disposer stack，实现创建失败逆序回滚；
- 明确 `ModelLayer.ready` 的错误消费契约；
- 可增加 `addModelAsync()`，或提供统一 status / error event；
- 即使保留 rejecting Promise，也应避免未观察时污染浏览器控制台。

#### 处理结果

- 新增 `ResourceScope`，Viewer 构造阶段的 renderer、canvas、纹理、manager、pass、controls、widgets 和 render loop 在创建后立即登记；后续同步装配抛错时按逆序继续释放，单个 disposer 失败不会阻断其余回滚；
- `Viewer.create()` 通过统一的 `awaitReadyOrDestroy()` 等待 renderer，WebGPU `ready` 拒绝时销毁完整 Viewer，同时保留原始初始化错误；
- `Viewer.ready` 内部挂载拒绝观察器，直接构造时不会产生未处理 Promise 拒绝；其公开契约明确要求调用方在失败后自行 `destroy()`，自动清理场景优先使用 `Viewer.create()`；
- `GltfModelLayer` 增加显式 ready 状态机，加载中移除会立即拒绝 `ready`；加载结束后的重复 resolve / reject 不会改变已确定结果；
- Model `ready` 保持可观察的拒绝语义，同时内部观察拒绝，调用方忽略 `ready` 时不会污染浏览器控制台；
- API JSDoc、Viewer API 文档和项目架构文档已同步生命周期契约；
- 新增资源逆序回滚、清理异常隔离、成功提交、异步失败销毁、模型加载中移除及加载失败测试；
- `pnpm type-check`、`pnpm build` 通过，42 个测试文件、159 项测试全部通过。构建仍有一条既有的 `MsdfAtlasLoader` 静态 / 动态重复导入提示，留待剩余项的零 warning 审计处理。

### EH-009：高频拾取路径存在规模化风险

**处理状态：已完成**

**修复提交：`812f320`（`fix: 收紧高频拾取调度与空间筛选`；2026-09-06 在 HEAD 祖先日志中核对）**

#### HISM

[src/controls/ViewerInteractionManager.ts](../../src/controls/ViewerInteractionManager.ts) 在存在 mousemove listener 时，每个原始 mousemove 都会执行拾取。

[src/hism/picking/HismPicker.ts](../../src/hism/picking/HismPicker.ts) 对每个可见 HISM mesh 的每个 instance：

1. 计算 instance matrix；
2. 做 bounding sphere 测试；
3. 对候选 instance 使用 proxy mesh raycast。

BVH 加速了单个 geometry 的三角形求交，但没有消除 instance 级线性扫描。

#### Entity

EntityPicker 同样会遍历实体；折线还需要遍历线段。大规模实体和 HISM 同时启用 mousemove 时，主线程压力会叠加。

#### 推荐整改

- mousemove 使用每帧合并或显式 throttle；
- HISM 拾取复用 cluster 空间结构，先筛 cluster，再筛 instance；
- 把 nearest 和 drill-all 使用不同策略及预算；
- 用已有 `benchmark:hism` 建立拾取基准，不只测渲染 FPS；
- 记录 p50 / p95 pick latency、实例数量、可见 cluster 数和候选实例数。

#### 整改结果与验证

- [src/controls/ViewerInteractionManager.ts](../../src/controls/ViewerInteractionManager.ts) 通过 `requestAnimationFrame` 合并原始 mousemove，同一帧只使用最后一个位置执行一次 nearest 拾取；移除最后一个 listener 或销毁 Viewer 时会取消待执行帧；
- [src/hism/core/HismCluster.ts](../../src/hism/core/HismCluster.ts) 在构建期缓存包含几何、实例旋转和缩放的精确簇包围体，避免固定 padding 对大尺寸实例产生漏拾取；
- [src/hism/core/HismLayer.ts](../../src/hism/core/HismLayer.ts) 先按可见簇和射线相交筛选候选，再进入 instance 级求交；
- nearest 按射线进入簇包围体的距离排序，并在后续簇不可能优于当前最近命中时停止；drill-all 保持遍历全部候选簇，不用固定数量预算破坏完整语义；
- 新增 `pnpm benchmark:hism:pick`，在 Node + Vite SSR 中直接构造真实 HISM 图层，不依赖示例服务或浏览器，并输出 p50 / p95 与完整遍历计数。

同一 Windows 主机、Node 22.20.0、50,000 instances、8 parts、324 个可见簇、100 次 nearest 拾取的结果：

| 状态 | p50 | p95 |
| --- | ---: | ---: |
| 整改前 | 1.422 ms | 2.295 ms |
| 整改后 | 0.308 ms | 0.561 ms |

整改后中心射线只产生 1 个候选簇、169 个候选逻辑实例、8 个候选 mesh，实际进行 1,352 次 mesh-instance 包围体测试并命中 8 次 instance 包围体。p50 降低约 78.3%，p95 降低约 75.6%。

聚焦回归覆盖 mousemove 帧合并 / 销毁取消、簇拒绝、超大缩放包围体、nearest 提前停止和 drill-all 完整遍历；`pnpm type-check`、`pnpm build` 通过，44 个测试文件、164 项测试全部通过。构建仍有一条既有的 `MsdfAtlasLoader` 静态 / 动态重复导入提示，继续留给 EH-010 的零 warning 收口。

- 或接受主入口静态包含，并删除无效动态 import；

### 7.3 发布原子性

[actions/release.js](../../actions/release.js) 当前顺序是：

1. 本地 commit + tag；
2. `pnpm publish`；
3. `git push --follow-tags`；
4. 创建 GitHub Release。

如果 npm publish 成功但 git push 失败，会形成 npm 已发布、远端仓库没有对应 commit / tag 的分叉状态。

建议至少增加远端权限和可推送性预检；更稳妥的方案是把发布流程做成可恢复的显式状态机，并记录每一步的完成状态。无论采用何种顺序，都必须有清晰的失败恢复手册。
