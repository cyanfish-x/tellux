## 1. 已确认的意图与范围

确认来源：2026-09-12 本次交互。用户纠正“玻璃和水折射……好像没有设定这个目标”，并对以下六项复述明确回复“正确”。这次确认规定方向，不证明任何候选算法已通过验收。

| 项目 | 当前依据与要求 |
| --- | --- |
| 结果 | 遮挡关系正确、性能良好的统一管线 |
| 使用者 | Tellux 应用开发者；不必反复为高斯、透明实体等分别修补阶段顺序 |
| 本轮交付 | 计划审查与防复发规则已完成；按用户后续“开始推进计划”执行阶段 0–3，阶段性结果不得替代最终验收 |
| 成功标准 | 技术选择对应实际问题，有成熟依据、适用边界和可验证结果 |
| 约束 | 优先复用 Three.js／Takram／Spark；必要扩展先证明缺口；当前版本达到 60 FPS，允许相对原错误管线有额外开销 |
| 范围外 | 本版暂缓云与对象穿插合成；新增玻璃／水折射、任意层数与体积交叠的物理精确合成；不借此次重构扩大公开 API 或承诺 WebGL／WebGPU 所有能力对等 |

本版按以下行为验收，具体场景与测量边界见最终记录：

- 高斯和透明实体跨地平线保持完整，不被天空分支抹掉；山体、建筑、镂空物的遮挡正确。
- 透明对象使用自身位置参与空气透视；现有显示参考颜色、局部光照、昼夜和标注策略不被静默改变。
- 普通透明、实体 OIT 与 Spark 的相互遮挡必须在实际组合中验证；云与场景对象穿插合成按用户确认暂缓，不作为本版退出条件。
- 相机移动、云运动、分辨率和开关变化时保持稳定；资源和输出有明确所有者。
- 引入的新管线不能靠降低原云质量、减少场景内容或撤销既有能力通过性能验收。

“采用成熟的实时近似”只规定选型原则。具体算法仍须说明采样方式、误差场景、维护代价和 Tellux 验证结果；不能把“UE／Unity 也近似”当作可见遮挡错误的豁免。

## 4. 从 UE／Unity 借鉴什么

以下官方材料于 2026-09-12 查阅。UE 文档页面当时标为 5.8；Unity 资料分别为 Unity 6 URP Render Graph 与 HDRP 17 雾。它们是架构和算法依据，不是对 Tellux WebGL、ECEF、高斯混合场景的性能或质量保证。

| 官方实践与来源 | 对本计划的启发 | 不作出的推论 |
| --- | --- | --- |
| [UE RDG](https://dev.epicgames.com/documentation/en-us/unreal-engine/render-dependency-graph-in-unreal-engine)由阶段声明资源依赖并管理生命周期 | 用显式读写关系和验证代替隐含 targetA／targetB 顺序 | 不照搬其 RHI、异步队列、内存别名或完整图编译器 |
| [Unity 6 URP Render Graph](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/render-graph-introduction.html)区分图内与导入资源 | Tellux 管自己分配的资源，借用上游资源时明确所有权 | URP 的资源管理文档不证明 HDRP 云或 Spark 的遮挡能力 |
| [UE Sky Atmosphere](https://dev.epicgames.com/documentation/unreal-engine/sky-atmosphere-component-in-unreal-engine)以 AerialPerspectiveLUT 服务不透明和透明网格 | 共享大气查询，避免为各类对象重复构造昂贵积分 | Takram 的 LUT 布局与 UE 不同；不直接复制体素尺寸或预设成本 |
| [UE 体积云](https://dev.epicgames.com/documentation/unreal-engine/volumetric-cloud-component-in-unreal-engine)采用低分辨率追踪、重建及散射近似，并区分实时与电影路径 | 保留云自身的高效流程，按可见问题选择最小接入 | Mode 2 不支持云与不透明网格相交；不能把任一模式宣传为全组合正确 |
| [UE 云模式变量](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-console-variables-reference)为半透明云合成列出全分辨率电影模式 Mode 3 | 云与透明的组合需单独核对具体模式及成本 | 该模式不是 WebGL 高斯实时穿插的低成本证明 |
| [HDRP 17 Fog](https://docs.unity.cn/Packages/com.unity.render-pipelines.high-definition@17.0/manual/Override-Fog.html)在低分辨率视锥三维网格上求值，提供深度切片与去噪控制 | 介质缓存及空间／时间分辨率是可比较的工程手段 | 雾的网格不能直接证明独立体积云的穿插正确，更不自动成为本项目待实现项 |

现有证据支持“显式编排、复用计算、按位置查询、按场景验证近似”的方向；尚不支持指定某一种云／高斯混合算法为已验证最佳方案。

## 5. 拟保留的最小架构

### 5.1 职责和阶段

先建立有限、可观察的阶段合同，不预建通用引擎框架：

1. Viewer 每帧提交一致的相机、时钟、场景和配置；单一所有者安排绘制。
2. 复用 Three.js 进行可见性和材质组分类，生成最近不透明／镂空表面的颜色与深度。
3. 大气模块提供共享 LUT／参数求值，天空与不透明表面只应用各自需要的贡献。
4. 普通透明、实体 OIT、Spark 通过内部适配器取得深度及大气参数，保持各自数据所有权；云的接入由已验证的组合方式决定。
5. 后处理、标注与最终输出按各自资源依赖执行，HDR、曝光和输出转换有唯一责任点。

无云场景已采用“不透明／镂空 → 天空及不透明空气透视 → 自身空气透视后的透明内容 → 后处理与输出”。本版有云场景复用同一提交阶段及既有云输出，完成现有功能回归；整张 overlay 不具备正确穿插能力，这一限制明确保留，不据此声称云穿插已经解决。

### 5.2 当前可确定的资源约束

| 资源 | 必须明确的含义 |
| --- | --- |
| 场景颜色 | 线性 HDR；是否已经包含照明、空气透视或云；禁止重复加入同段散射 |
| 不透明深度 | 编码、清空值、投影、near／far、DPR 和 resolve；采样纹理与硬件深度附件不是同一件事 |
| 透明贡献 | 预乘 alpha、coverage 与混合方法；RGB 介质透射率不能混作 alpha |
| 大气参数／LUT | 一致时钟、光源、ECEF／相机相对变换、米与 LUT 单位；保持现有显示色策略 |
| 上游云资源 | 借用的输出、相机／尺寸／帧有效性及负责释放的所有者；原输出与新增输出不能混淆 |
| 历史与最终输出 | 相机切换、resize、云运动、显露等失效条件；唯一曝光、色调映射和色彩空间转换 |

新阶段不得在冲突的 framebuffer 读写同一资源；多次 scene submission 的阴影、回调、透明片元贡献次数须核对。必要的深度／法线 pass 与“重复绘制一次完整场景”分别计数。

这里不预定义 `mediumSegments`、折射世界查询或通用透明层容器。选择云适配方式后，只为已证明必要的内容增加内部资源合同。

## 6. 调整后的实施顺序

新阶段使用 0–3 编号，避免将旧 A1–A3 的研究状态误读为进度。阶段 0–3 已按本版范围完成：接缝、编排与兼容、有限混合透明、工程与文档均有验证记录。云专用实验停止，后端能力边界保持不变。下表保留各阶段交付要求，验收结论见文首最终记录。

| 阶段 | 交付 | 退出条件与决策点 |
| --- | --- | --- |
| **0：基线与最小接缝验证** | 复用三个初始原型与真实高斯入口；固定场景、相机、配置和帧成本；验证 Three.js 阶段拆分、材质组、阴影／回调及深度交接；列出云组合信息缺口 | 地平线／山体问题能复现，修复对照可观察；已知每项额外 draw／target 的来源。无需完成联合积分与折射实验 |
| **1：编排与透明大气接入** | 演进现有单一管线所有者；接入普通透明、实体 OIT、Spark 的深度和共享大气；保持既有颜色及后处理语义 | 无云与原有无透明场景通过；有云场景完成现有功能回归并明确暂缓穿插。此时不宣称全部混合透明遮挡已完成 |
| **2：混合透明遮挡** | 对跨 Spark／OIT／普通透明的前后及交叉验证并接入必要分段；保留各自颜色、数据、排序与资源所有权；云穿插延期 | 真实高斯及实体组合的遮挡、运动通过；新增深度／颜色资源的边缘和生命周期通过；完整实际用例在确认的 1080p 环境达到 60 FPS |
| **3：后端、工程与交付** | 在当前支持组合内演进 WebGPU 契约；回归后处理／标注、多个 Viewer、resize、销毁；同步文档与 skill，检查构建及依赖边界 | 所有本次声明支持的组合完成浏览器与性能验收；WebGPU 尚不支持的云／Spark 等能力明确列出，不扩大承诺 |

阶段 1 的阶段性通过不代替混合透明和最终兼容验收。云专用资源、积分和历史表示不再生产化，本版只回归现有云功能。

- **保留**：Takram 的天气／密度／照明、采样质量、LOD、云影及原有低分辨率路径。原历史只能在其语义未改变的资源上复用。
- **首个对照**：原流程与仅改变编排／资源接入的结果。在明确空间分离的用例验证前后关系，并在穿入、多层用例证伪整图前后交换。
- **必要时的候选扩展**：在原步进中记录有限查询深度处的累计贡献，或使用已有输出作有边界的合成。两者均是待测候选，不能从代表深度恢复不存在的分布，也不能直接将纯云结果称为联合介质结果。
- **成本检查**：分别记录额外输出、带宽、透明重复 draw、GPU 时间；不能将多次运行整套云更新当作一次复用。若需修改积分、历史或增加多层资源，先记录必要性与更小方案失败的证据。
- **退出**：能回答该缺口是否可用有限扩展解决。若不能，输出失败用例、测量与替代路线再审查；不在实验内部无期限扩成新的云渲染器。

## 7. 验收与性能口径

### 7.1 实际行为矩阵

| 场景 | 检查 |
| --- | --- |
| 跨地平线的透明柱与真实高斯 | 天空不能抹掉对象；前方山体／墙保留正确遮挡 |
| 混合材质组、镂空和普通透明 | 不漏组、不重复透明累积；阴影与回调不因分阶段改变行为 |
| 普通透明、实体 OIT、Spark 前后及交叉 | 分别确认组合边界；不以 Spark 自身排序通过替代混合排序 |
| 云现有功能 | 云开关、形态、照明和运动正常；云前／云后／穿入对象的空间合成正确性暂缓 |
| 细柱、墙边、地平线、遮挡显露 | 检查本版透明深度分段的边缘有效性；不新增云低分辨率／历史的穿插验收 |
| 地面／高空、正午／日落／夜间、相机与云运动 | 自身空气透视、颜色一致性、时间稳定性；不凭静止截图签收 |
| 既有 transmission、标注、EDL、高亮与其他受影响效果 | 保持原生行为，不借兼容回归新增折射功能；按实际资源说明透明深度能力 |
| DPR／resize／相机切换、多 Viewer、开关／销毁／恢复 | 资源有效、无残留、无重复所有者及 shader／GL 错误 |

独立页面与 Sandcastle 均覆盖受影响入口，包含实际 `gaussian-splat-3d-tiles` 数据场景。数值参考只回答对应误差问题；高采样参考不是物理真值。严重遮挡错误不能用全图平均误差掩盖。

旧稿“轮廓 1 像素、显示 RGB p95 0.02”等是未采纳的统一阈值，不继续作为产品签收标准。对需要量化的误差，在具体用例中说明参考、区域、分辨率和阈值依据，再固定验证；不得看到失败后放宽标准。已有数值测试阈值继续用于它们原本的算法回归。

### 7.2 性能

- 当前交付目标为用户在 2026-09-13 明确更新的 **1920×1080、DPR 1、RTX 3060 Ti、60 FPS**，对应约 16.67 ms／帧。基于完整场景更新与绘制报告实际帧率、CPU／GPU 帧时间；单个 pass、排除 tileset.update 的 Viewer.render 或少量静态帧不能单独证明达标。数据加载期与稳定渲染期分开记录。
- 同硬件／驱动／浏览器、后端、物理分辨率／DPR、相机／数据规模、太阳／云状态和质量，对比原方案与候选，解释新增成本。检查功能关闭和实际启用组合；相对旧方案慢本身不再构成否决理由，只要最终实际用例达到本版目标。本次 1080p 由用户重新明确确认，不是沿用旧计划假设。
- 交错配对，分别记录 CPU 提交与整帧 GPU p50／p95、分阶段时间、draw 次数及新增资源 MiB。预热、采样和异常保留规则在测前固定；受帧率限制与连续负载测量分别报告。
- 原方案的错误画面不是视觉参考，但仍是约束成本的基线；若独立数值修复改变了采样成本，同时列原始、单独修复、编排候选，不混淆收益来源。
- 无 GPU timer 则明确 GPU 结论缺失。差异落在噪声中时报告“未能判定”，用重复配对和差值分布核实；不能宣布精确相等，也不提前允许固定百分比回退。
- 参考积分 draw、验证读回和生产整帧分开。高成本参考只在有明确判断用途时运行，不能为缩短参考耗时另开无限微优化主线。

TypeScript 行为变化时按 AGENTS 跑类型检查；发布面变化时跑构建。有关浏览器与工程检查随实现完成；以各阶段证据明确通过范围，不能从计划文字推导性能或画面通过。

## 9. 后续任务的执行约束

- 先读第 1 节确认需求来源，再检查任务是否直接服务于第 7 节的实际用例。
- 改上游核心前，写清复用路径、最小缺口、扩展范围与反例；更换核心算法、扩大能力或改变质量目标需要单独审查。常规实现、调试和验证继续自主完成。
- 实验在运行前写明待判断问题、对照、成本范围与停止条件；足以决定路线后停止扩展，不将研究完整性当作产品进度。

- 每次结果区分：代码存在、实验执行、目标验收、性能通过。失败或未完成项保持明确，不用扩大研究或降低标准来绕过。
